# Billo

Mobile-first bill splitting for friends at the table, with receipt extraction and external payment handoffs.

## Run locally

```bash
pnpm install
export DATABASE_URL=postgres://...      # any Postgres
export OPENAI_API_KEY=sk-...            # optional: receipt scanning
pnpm db:push                            # create tables
pnpm dev:api                            # Express API on :3001
pnpm dev:web                            # Vite on :5173, proxies /api to :3001
```

Other: `pnpm typecheck`, `pnpm test`, `pnpm --filter @workspace/api-spec run codegen` (regenerate API hooks/Zod from OpenAPI).

## Deploy on Vercel

1. Import the GitHub repo in Vercel. `vercel.json` already sets the install/build commands and output directory (leave Framework Preset as "Other").
2. Add a Postgres database (Storage → Neon via Marketplace). It injects `DATABASE_URL` / `POSTGRES_URL`.
3. Create the tables once: `DATABASE_URL=<prod url> pnpm db:push`.
4. Optional env vars: `OPENAI_API_KEY` (receipt scanning; without it users enter receipts manually), `OPENAI_BASE_URL`, `OPENAI_RECEIPT_MODEL`.
5. Deploy. The static frontend is served from `artifacts/billo/dist/public`; every `/api/*` request is handled by one bundled Express serverless function (`api/index.js`, generated by `pnpm run build:vercel`).

Notes: rate limits are in-memory, so they are per function instance (best effort). Receipt uploads are capped by Vercel's ~4.5 MB request body limit, so large photos should be downscaled client-side.

## Where things live

- `artifacts/billo/` — real app, served at `/`.
- `artifacts/mockup-sandbox/src/components/mockups/split/` — preserved visual prototype, not the real application.
- `lib/api-spec/openapi.yaml` — API contract and generated clients.
- `lib/db/src/schema/bills.ts` — durable bills and participant sessions.
- `artifacts/api-server/src/lib/billo-domain.ts` — integer-cent allocations, validation and finalization.
- `artifacts/api-server/src/routes/billo.ts` — bill, join, mutation and receipt-scan routes.

## Architecture decisions

- No signup is intentional: private HttpOnly session cookies authorize each browser's participation. A shared invitation must never grant payer access.
- Receipt images are sent transiently to the AI provider for extraction, not saved by Billo. Store extracted data only after review.
- A finalized bill is immutable apart from participants' self-reported paid status. External payments cannot be reversed by editing a bill.
- Polling keeps participant views current; do not substitute local-only state for shared bill mutations.

## Product

Receipt camera/upload/manual entry, tap-to-select items shared equally among their selectors, link and QR invitations, payer receipt/tip confirmation and finalization, Venmo handoff, Zelle copyable details, and self-reported payment tracking.

## Gotchas

- Zelle runs inside participating banks; do not invent a universal prefilled Zelle app link.
- Venmo custom-scheme behavior depends on device and app installation. Keep web and copy fallbacks, and never treat opening a link as a confirmed payment.
- Bill writes are serialized by database row locks. Own-item selections do not reject unrelated revisions. Receipt replacements guard against newer receipt edits only and preserve selections on unchanged items. Open legacy bills are converted once under the row lock when read or changed; closed bills retain their original amounts.
